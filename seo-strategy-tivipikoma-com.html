56 D Overall Health

Solid brand and offer, but the site is nearly invisible in search — and gives away link equity it doesn't have to spare

tivipikoma.com has real strengths for a small IPTV brand: Dutch-language copy, JSON-LD across every page, FAQ schema, a real H1 on every page including the homepage (via motion.h1), and per-page <title>/meta updates on 4 of 7 URLs. But three blog/list URLs never get a real canonical tag, Open Graph and Twitter Card data are frozen on the homepage's values site-wide, and — most urgently — a live search for "tvpikoma abonnement" surfaces nine near-identical copycat domains before tivipikoma.com shows up at all. Fix the on-page basics first; the brand-collision problem needs a decision from you (see Executive Summary).

Key Findings
The single biggest problem isn't on the site at all: a live search for "tvpikoma abonnement" and for generic terms like "IPTV Nederland kopen" returns nine confusingly similar domains (tvpikoma.us, tvpikoma.one, tvpikoma.co, tvpikoma.me, tv-pikoma.shop, tv-pikoma.store, tvpikomatv.com, iptvpikoma.nl, and a Trustpilot page for a *different* tvpikoma.com) — but not tivipikoma.com. Whatever the relationship between these sites, your actual domain is not visible for its own brand name, which undercuts every other SEO effort on this list. On-site, the three /blog URLs never set a canonical tag via JavaScript, so they inherit the homepage's canonical and effectively tell Google they're duplicates of "/". Because tivipikoma.com is a pure client-side-rendered React SPA (react-router-dom + a catch-all rewrite in vercel.json) with no server-side rendering, every route ships the exact same static <head> — meaning Open Graph and Twitter Card tags never change per page, so sharing an /abonnementen or /blog link on WhatsApp (the business's primary channel) always previews the homepage. The FAQPage JSON-LD present on every page lists 6 Q&As that don't match any of the 7 questions actually shown in the on-page FAQ component — a structured-data mismatch that risks losing the FAQ rich result entirely. Internally, /abonnementen, /reseller-pakket and /3maanden-Gratis each link to only one other page (the homepage logo), and neither blog post links to /abonnementen — the page a reader comparing IPTV providers should land on next.

Client-Side Rendering — Why This Matters Here
What a non-JS-executing request actually sees

Fetching any of the 7 URLs directly returns only the static <div id="root"></div> shell

Confirmed on live pages: the raw HTML response for "/", "/abonnementen" and both blog posts contains only the static head (one shared title/meta/schema block) and an empty root div — all visible content, headings, and page-specific text is injected by React after the bundle loads. Modern Google web-rendering does execute JavaScript before indexing, so this alone won't stop the site from being indexed — but it does mean: (1) any tool, crawler, or social-media link-unfurler that doesn't execute JS sees the homepage's generic metadata regardless of URL, and (2) rendering happens on a delayed "second wave" in Google's pipeline, so fresh content (like the two blog posts published this week) can take longer to be fully evaluated than on a server-rendered or statically-generated site.

Not necessarily worth a framework migration for a 7-page site — but it raises the cost of every other JS-only fix on this list (canonical, OG tags, schema), since none of it is visible to anything that doesn't render JS. If organic growth becomes a bigger priority, consider prerendering (e.g. vite-plugin-ssr, or a static prerender step for the 7 known routes) so each URL ships its own real HTML.
